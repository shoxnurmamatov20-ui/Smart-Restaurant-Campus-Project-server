# Go-live — the keys the code is waiting for

Everything in this table is **built and tested behind a driver**. Without the
key the product runs in an honest fallback (the SMS goes to a log file, the
fiscal square stays a chequerboard, the online rail is not offered). With the
key it is one line in `/srv/srcp/shared/env/api.env` and `sudo srcp-deploy`.

Nothing here needs code. That is the point of the table: a restaurant can go
live the day the last row is filled in, and the order of the rows is the order
that unblocks the most.

## And three things that are not keys

- **Your own platform account.** The seeded `admin@campus.uz` carries a
  TOTP key that is written in the repository. Make one that is yours:
  `sudo -u srcp php /srv/srcp/current/apps/api/artisan admin:create
--email=you@… --name="…"` (asks for a password), then
  `… artisan admin:two-factor you@…` — it prints the authenticator key once.
  Sign in at `/admin` with the password and the six-digit code; restaurants
  are created there (`Tenants → New`) or with `restaurant:create-owner`.
- **A real owner.** The demo accounts are locked. Create the restaurant that
  will actually trade: `sudo -u srcp php /srv/srcp/current/apps/api/artisan
restaurant:create-owner --restaurant="…" --name="…" --email="…"`. The
  password is printed once.
- **A lawyer.** `/terms` and `/privacy` are drafts with thirteen
  `[to'ldirilsin]` placeholders — the legal entity's name, STIR, address, bank,
  the data-registry number. They are listed in `legal.test.ts` so none is
  forgotten.
- **The signing key.** `~/.srcp-android/release.keystore` + `signing.env` is
  the identity of every installed APK. Copy it somewhere that is not this
  server today.
- **Where the photographs live — and when to move them.** Dish photographs
  need no key: `MENU_IMAGE_DISK` defaults to `public`, which is
  `shared/storage/app/public` on this box, served by nginx from disk under
  `/storage/dish/` with a year of cache. Every upload is re-encoded to three
  WebP sizes (about 160 KB per dish, whatever the phone sent), so the disk
  grows by roughly a gigabyte per six thousand dishes. The day that is a
  second server rather than a bigger disk, set `MENU_IMAGE_DISK=s3` with the
  `AWS_*` block (MinIO or S3) and point `AWS_URL` at the CDN in front of it,
  then copy `storage/app/public/dish/` into the bucket under the same keys —
  addresses are built from the disk at read time, so no row changes. Until
  then the daily `srcp-backup` must include `shared/storage/app/public`: a
  photograph is the one thing in this product the database cannot rebuild.
- **Real customers, when there are some.** The public site no longer claims
  any. It used to: three case studies with named owners and named restaurants,
  three quotes from the same invented people, "42 restoran, 118 filial" in the
  hero pill and in every shared link card, a per-city restaurant tally, and an
  ROI note justifying its percentages with "the average across 42 restaurants".
  All of it is now framed as what it is — modelled scenarios, attributed to a
  role, with the modelling said out loud — and the four figures under the hero
  are facts about the software (24 sections, 14 modules, 3 languages, 4 till
  modes) rather than about its sales.
  `apps/web/src/app/(marketing)/honest-claims.test.ts` is what stops the names
  coming back. When the first real restaurants agree to be named, their words
  and their figures replace the scenarios — that is a content change, and the
  test names the files.

## How to check a key landed

```bash
sudo srcp-health                                    # every driver reports itself
curl -s https://<host>/api/v1/public/payments/providers  # rails offered to a guest
curl -s -H 'Authorization: Bearer <owner token>' -H 'X-Tenant: <slug>' https://<host>/api/v1/finance/fiscal/probe   # OFD handshake
```
